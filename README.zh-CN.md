# BLIND

### 保护隐私的语义发现协议

让两个陌生人发现需求上的匹配，无需先向发现服务运营方公开自己的具体意图；只有双方同意后，才交换获准披露的联系方式。

**研究提案 · RFC-0001 · v0.3 草案 · 2026 年 10 月**

[English](README.md) · [完整 RFC（英文）](docs/rfcs/0001-private-semantic-rendezvous.md) · [研究路线图](docs/ROADMAP.md)

## BLIND 想解决什么问题

一个人提供某种产品或服务，另一个人正在寻找它。双方希望发现彼此，却不想公开详细描述、需求条件和联系方式。

BLIND 探索一种流程：在各自设备上理解自然语言描述，将受密码学机制保护的输入交给计算层进行匹配；满足条件时产生受限邀请，再由双方分别决定是否建立联系。

双方不必使用完全相同的词，也不必从固定标签目录中选择需求。

## 预期流程

本地描述意图 → 本地语义编码 → 保护匹配输入 → 私密兼容性计算 → 受限邀请 → 双方独立同意 → 交换获准披露的联系方式。

后续沟通转入独立的端到端加密渠道。消息时序、通知和连接行为可能泄露信息，需要纳入协议分析。

## 主要设计

| 环节 | 提案中的设计方向 |
|---|---|
| 本地理解 | 使用统一版本的编码配置，在设备上处理自由文本 |
| 判断匹配 | 综合角色、语义接近度和可选的私有约束 |
| 私密计算 | 研究由两个独立运营节点执行 MPC 的参考方案 |
| 最少披露 | 输出受限邀请，不公开精确分数或匹配排名 |
| 双方授权 | 两人分别同意，并将授权绑定到特定会话 |
| 初期验证 | 从有限规模的匹配池开始，测量效果、开销和信息泄露 |

双节点方案依赖不串通假设。语义向量仍属于敏感输入；相似度也不等于交易可行性或真实需求的概率。

## 当前进展

目前发布的是**研究提案与实验计划**，尚未提供可运行应用、密码学实现、实测性能、安全证明或独立审计。文中的 RFC 表示本项目征求意见稿。

项目研究现有技术如何组合，不主张绝对匿名、零信息泄露或全球首创。支付、结算、聊天，以及参与者陈述的真实性验证均不属于当前范围。

## 下一步

1. 验证语义匹配：同义表达、跨语言描述与容易误判的样本。
2. 比较明文基线和受保护计算的误差与开销。
3. 测试反复探测、伪造输入、多身份和授权攻击。
4. 研究异步发现、过期、节点故障与元数据泄露。
5. 对具体协议与实现开展独立评审。
